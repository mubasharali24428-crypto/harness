# Local application demo: failing test to reviewed fix

This is a recording candidate, not a current end-to-end certification. The strongest existing evidence is the real VS Code extension workflow in `docs/demo/yc-demo-runbook.md` and the dated W24 evidence under `docs/briefs/evidence/w24/`. Those are historical results, not proof that today's stack works. The seeded web demo is a recorded replay; do not present it as a live run. The plan shown in the historical workflow was a fixed template, not a model-generated task-specific plan. Multiplayer, production readiness and customer safety are not established by this demo.

## Prepare and rehearse

1. Start the existing local stack using the established operator runbook, `docs/runbooks/redeploy-worker-and-orchestrator.md`, only after checking the current stack and image versions. Do not point it at customer data. Confirm the provider configuration and budget privately; do not display or print credentials. The VS Code extension package and a working local model/provider, local services and sign-in are required. This setup was not verified on 2026-11-11 because the local Docker daemon was unavailable.
2. From the repository root, run `python3 scripts/demo/techstars_fixture.py`. It prints a newly created temporary directory; it never resets an existing directory. Open that directory in VS Code with the Harness extension installed and sign in to the local stack before recording. Verify the extension points to the intended local stack and workspace. The older `scripts/demo/yc_demo_vscode.sh` deletes `~/harness-demo` on every run; do not use it if that path contains anything to preserve.
3. In the workspace terminal run `python3 -B -m unittest -v`. The `-B` option avoids stale bytecode during rapid rehearsals. Confirm the `add(2, 3)` test fails with `-1 != 5`. Keep the output visible. If it does not fail, start with a fresh fixture.
4. Open `calc.py`, run **Harness: Run on selection**, choose the whole file and no additional context, and request: `Fix add() in calc.py so that python -m unittest passes, then run python -m unittest to confirm. Do not edit the test.` Review the plan dialog and approve it yourself. Describe the plan as a displayed template unless a current rehearsal establishes otherwise.
5. Wait for the actual run and its result. Review the reported test result and diff, then confirm and approve the `calc.py` change. If a run fails, changes unexpected files, or cannot provide a review, stop and record that failure rather than staging a result. Run `python3 -B -m unittest -v` again in the workspace terminal to verify the applied bytes independently. Inspect `calc.py` and `test_calc.py`; the test must remain unchanged.
6. Show the actual available run/review record, if accessible. Historical automated W24 evidence checked plan approval, review state and patch digest on the server, but availability and completeness must be verified in the current session. Do not claim a complete audit trail from a result summary alone.
7. Rehearse the full sequence at least twice with separate fresh fixtures, recording date, revision (`git rev-parse HEAD`), stack image tags, model, run IDs, outcomes and failures privately. Only record the live sequence if it succeeds reliably. The optional automated rehearsal `node clients/vscode/scripts/w24_window_run.mjs` spends on one real model call and drives a real window; it uses fixed scratch paths and writes evidence, so inspect the script and existing files before running it.

## Suggested short shot sequence

Show the failing terminal test; enter the goal; show the plan and human approval; show the actual run and review; approve the diff; rerun the test and show it passing. Keep waits or cuts honest and label any cut. If the live run cannot be rehearsed, use historical screenshots only if clearly dated and labelled as a previous recorded run; do not imply they are live. This is a single local engineering task, not a demonstration of the planned multiplayer product or a customer-ready pilot.
