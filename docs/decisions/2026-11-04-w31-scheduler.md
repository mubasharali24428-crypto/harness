## The question this settles

W31 asked whether adapting the Scheduler's timetable-specific contract is worth
shipping, compared with a fresh OR-Tools model on synthetic agent workloads. The
Scheduler is an academic timetabling optimizer, not the Harness run queue. Its
frozen shapes are sessions in rooms on a 08:00-18:00 week grid, with 60-180
minute blocks and no dependencies, deadlines or priorities.

Two things had to be separated:

1. Is the **timetable contract** a usable integration surface for agent tasks?
2. Is a **neutral allocation model** beside that contract worth keeping?

## Decision

1. **PILOT the neutral allocation contract and model.** The Scheduler gains
   `solver/allocation_types.py` (pure-dict request: tasks, durations, capability
   tags, dependencies, deadlines, priorities, resources with capacity and
   availability) and `solver/allocation.py` (interval CP-SAT). The frozen
   `Session`/`Room`/`ChangeRequest` shapes and `Solver.solve()` are untouched.
   W32 may use this module as a **proposal source** behind the existing approval
   boundary.
2. **REJECT the timetable bridge as a product path.** It stays in
   `experiments/w31-scheduler/` as evidence. Duplicating rooms to emulate
   capacity and dropping dependencies/deadlines/priorities is not a safe general
   adapter; those losses are reported rather than hidden.
3. **Do not vendor or redistribute Scheduler code.** That repository has no
   `LICENSE` file. W31 imported it by path (`SCHEDULER_ROOT`) and copied nothing
   into the Harness. Any distribution or bundled deployment needs an ownership
   and license decision first; this record does not make one.
4. **Keep the independent validator as a required gate.** Every solver result in
   the experiment was checked by `w31/contract.py`, which shares no solver
   internals. A future proposal source must pass the same check before a reviewer
   sees it as valid.
5. **No dispatch, no permissions change.** The experiment performs no real
   execution and adds no authority. W32 owns the approved-plan-to-execution path.

## Evidence

Synthetic workloads of 10, 50, 100 and 200 tasks, fixed seed, OR-Tools 9.15.6755,
median of three runs. Full data and all samples:
[`report.json`](../../experiments/w31-scheduler/report.json).

| Workload | Fresh time-indexed | Scheduler interval | Result |
|---|---:|---:|---|
| Feasibility, 10 tasks | 279 ms | 6 ms | both complete and valid |
| Feasibility, 50 tasks | 2,557 ms | 25 ms | both complete and valid |
| Feasibility, 100 tasks | 4,505 ms | 56 ms | both complete and valid |
| Feasibility, 200 tasks | 6,514 ms | 127 ms | both complete and valid |
| Optimized (10 s), 10 tasks | optimal, 530 ms | optimal, 28 ms | same optimum (makespan 4, weighted 61) |
| Optimized (10 s), 50 tasks | feasible, makespan 40 | feasible, makespan 54 | fresh better on makespan |
| Optimized (10 s), 100 tasks | feasible, makespan 100 | feasible, makespan 98 | Scheduler better |
| Optimized (10 s), 200 tasks | unknown, no assignment | feasible, makespan 100 | Scheduler only |

The timetable bridge solved every expressible workload (65-1,035 ms) and every
mapped result passed the allocation validator, but only because the workload was
pre-filtered to what the contract can represent. On the full contract it reports
dependencies, deadlines, priorities, durations outside 60-180 minutes and
horizons beyond 100 slots as unrepresentable.

Tests: 19 in the Scheduler's `solver/test_allocation.py`, 42 in
`experiments/w31-scheduler/tests/`, the full Scheduler solver suite (202 tests),
and the Harness static gates. The experiment is intentionally not in the Harness
CI matrix because it needs an external, unlicensed repository plus `ortools`.

## Options considered and rejected

| Option | Why rejected now |
|---|---|
| **Ship the timetable bridge as the integration surface** | It cannot express dependencies, deadlines, priorities, arbitrary durations or horizons beyond one week; capacity > 1 only works by duplicating rooms. Pre-filtering workloads hides the gap instead of closing it. |
| **Vendor the Scheduler's neutral module into the Harness** | No `LICENSE` file in that repository. Copying code would decide distribution rights that W30 and the owner have not settled. |
| **Reject the Scheduler and keep only the fresh Harness model** | The time-indexed model is 51-102x slower in feasibility mode and failed to produce any assignment at 200 tasks in 10 seconds. It remains useful as an independent cross-check, not as the primary planner. |
| **Ship the Scheduler as a product dependency now** | Same license gap plus an unresolved operating model (process boundary, version pinning, failure handling). W31 is an experiment, not a deployment. |
| **Treat the heuristic timetable result as an optimized plan** | The default timetable engine is a constructive heuristic; its speed is not evidence of objective quality, and it has no dependency/deadline fields to optimize. |

## Consequences

- W32 gets a concrete interface to build on: pure-dict proposals in, validated
  assignments out. The Harness queue, policy, approvals and worker lifecycle are
  unchanged and remain authoritative.
- The Scheduler repository now has a second, additive contract. Its timetable
  tests and goldens are untouched; the new module is pure dicts with no Django.
- The fresh model stays in the experiment as a cross-check. If the two models
  disagree on a future workload, the independent validator decides which result
  is valid, not which solver is preferred.
- Optimization quality at a fixed budget is workload-dependent (fresh better at
  50 tasks, Scheduler better at 100 and 200). W32 should set an explicit budget
  and record the status (`optimal` vs `feasible`) rather than presenting every
  result as optimal.

## Triggers to revisit

- A `LICENSE` or ownership decision for the Scheduler repository.
- W32 approval to connect proposals to execution, or any request for automatic
  dispatch (not granted by this record).
- Workloads above 200 tasks, horizons above 100 slots, or objectives beyond
  makespan/weighted completion.
- A change to the neutral contract's frozen shape, which needs an A0 stamp in
  the Scheduler repository as well as a Harness review.
