# Harness roadmap — from a governed sandbox to a launchable product

Prepared 2026-10-25. Target: a product that is **functional, working and
feature-complete against the union of Claude Code + Codex + the DeepSeek
harness + Muse-class builders**, with our governance story intact — and with
**Hermes**, our own language and compiler, woven through it as the verification
substrate, the safe plugin runtime and the reference language for the editor
surface (see PART B, from W2).

Honest framing up front: this is ~20 weeks of focused work for one engineer
plus agents (18 product weeks + ~2 incremental Hermes weeks that interleave
rather than stack), and roughly 11–13 weeks if two engineers run in parallel.
Weeks are ordered by dependency, not by excitement. Every week has an exit gate
— if a gate isn't met, the following week's plan is wrong and we re-plan rather
than slide silently.

One naming note: I've read "Muse" as the agentic app-builder class (live
preview, deploy-from-prompt — Lovable / Cursor Composer / Bolt). If you meant a
specific product, the items that shift are W11–W12 (preview + deploy), not the
rest.

---

## What we already have (do not rebuild it)

OS-enforced confinement (Landlock + Seatbelt + shell gate + egress proxy),
plan approval before any execution, per-batch git checkpoints, durable run
queue, multi-actor agent tree (built, unwired), per-team cost ledger and tier
caps, append-only audit with secret and reasoning scrub, SSO + OIDC drill,
BYOK across 65 providers over three wire protocols, self-hostable compose
stack, DPA-shaped legal packet.

Most of what the leaders have that we lack is **already inside the SDK runtime
we ship**, switched off. That reframes this whole plan: less construction, more
wiring and review.

## Ground rules for every week

1. No fake affordances. If a control cannot do the thing, it is disabled with a
   reason or removed. (Batch A found several; the audit is a standing gate.)
2. Frozen `contracts/` changes need a version bump plus mock updates in the same
   PR. Two contract changes are scheduled: W2 (tool events), W9 (artifact
   types). Everything else avoids touching them.
3. Security changes ship with the enforcement, never after. A new capability
   that widens the agent's reach lands with a test that proves the boundary.
4. Every week ends with the full gate green: section suites, `make
   static-gates`, section7 tsc/vitest/build, live smoke on the compose stack.

# PHASE 1 — It works and you can watch it (W1–W4)

## W1 — Fix the outage, then wire what the SDK already does

*Day 0:* `sandbox-egress` crash-loops (no `HARNESS_MASTER_KEY`, no dev opt-in)
→ `harness-sandbox` 503 on `/ready`, 708 failed healthchecks, hidden by the
demo replay. Fix env, decide whether sandbox readiness should depend on egress
at all, add an unhealthy-container smoke test.

- Flip `tool-fs` `read/write/edit` on (all `false` today, verified in the
  runtime binary) **after** confirming the fs tool honours our workspace scope;
  add glob/grep tools.
- Pass `on_notification` to `harness.run()` and stream tool calls → live
  transcript with per-call duration, outcome, collapsible output, running
  token/cost/elapsed footer. **Needs the W2 contract bump decision on day 1.**
- Stop stripping `.git`; remove the hardcoded `max_tokens=4096`; surface the
  1M window and compaction state the profile already runs.
- Goal attachment path so a screenshot reaches the model (`readImage` is
  already on).

**Gate:** a live run executes end to end on a healthy stack; you can watch each
tool call; a screenshot-driven "fix this UI" task succeeds; the `python -c`
write bypass is closed or documented as OS-enforced.

## W2 — Context, memory and the contract bump

- Contracts: `tool_call` / `tool_result` event types, version bump, mocks.
- Baseline repo context injected into the prompt (tree, README, git status,
  dependency manifests) — the runtime's `includeRuntimeContext` is currently
  forced off.
- Loop detection + stuck-run recovery; retry-with-changes as a *visible*
  affordance instead of the deleted model ladder.
- Project rules: `project_rules` reaches the planner today; extend it to the
  executing agent (this is our `CLAUDE.md` / `AGENTS.md` equivalent, and it's
  already a DB row rather than a file).

**Gate:** a run in a 500-file repo finds the right files without being told; a
deliberately looping task is caught and stopped with a message, not a budget
burn.

## W3 — Control: interrupt, steer, approve in-loop

- Cancel channel into the engine worker (`Session` has no cancel — likely
  SIGTERM + resume-from-checkpoint; design first, 2 days of spike before code).
- Mid-run steering queue that the agent drains between tool calls.
- **In-loop human approval** (the leaders' permission prompts). Needs your
  policy call: which classes of action require approval, and does a team opt
  into auto-accept. Deny-only is safer but pushes users to disable it.
- Rewind-to-checkpoint from the UI (S5 already stores the pairs).

**Gate:** stop a run mid-tool and resume from its last checkpoint; approve a
dangerous command from the UI and watch it proceed; reject it and the agent
adapts.

## W4 — Reach: web, packages, MCP client

- `web_fetch` tool behind an explicit egress decision (the allow-list predates
  the provider registry and must be derived from it).
- Mount the SDK's MCP client with a reviewed server allow-list — we expose an
  MCP server today but cannot consume one, so we can't reach Slack, Jira, or
  internal APIs.
- Dependency/package awareness: read lockfiles, run installs inside the
  sandbox, cache the workspace between runs.

**Gate:** an agent answers a question that requires reading live docs; a run
uses a third-party MCP tool and the audit records it.

**Phase 1 review:** at this point we are functionally a credible Claude Code /
Codex alternative for a team, with better governance and no editor surface.

# PHASE 2 — Surfaces people actually live in (W5–W9)

## W5–W6 — The CLI

A first-class terminal agent (`harness run`, `harness chat`, `harness diff`)
talking to the same services, same policy gate, same audit trail. This is the
biggest single adoption lever: developers will not open a browser to fix a bug.
Includes local-workspace mode with the same confinement, offline token storage,
and a non-JSONL scriptable output mode.

**Gate:** the same task completes from the CLI and the web, with identical audit
events.

## W7 — IDE extension (VS Code)

Inline diff at the point of work, `@`-symbol context picking (files, symbols,
git hunks), selection-as-context, status bar run indicator, approve/reject from
the editor.

**Gate:** an edit proposed in-IDE round-trips through the harness policy gate —
the extension must not become a way to bypass confinement.

## W8 — Parallelism and worktrees

Per-run git worktrees so N runs touch the same repo without colliding; a real
queue UI with priorities; wire the **agent tree to actual execution** (built,
and its own docstring says nothing calls it today).

**Gate:** three concurrent runs in one repo, each isolated, each reviewable,
none clobbering another's checkpoint.

## W9 — Artifacts, previews and the Muse-class loop

- Contract change #2: artifact types (screenshots, logs, build outputs,
  preview URLs).
- Live preview of what the agent built, with a share link.
- Deploy-from-run to a hosting target (our own `sites`-style target or a
  customer's), gated by the same approval model.
- Share links / public transcripts with the scrub rules we already have.

**Gate:** prompt → working app → public URL, with the whole chain audited and
revocable.

# PHASE 3 — Depth and differentiation (W10–W14)

## W10 — Browser use and computer testing

Headless browser control inside the sandbox (the runtime ships Playwright for
our own a11y tests — reuse that machinery), screenshots back into context, and
an agent that can verify its own frontend change instead of asserting it.

**Gate:** a UI bug is reproduced, fixed and re-verified by the agent with
before/after screenshots attached to the run.

## W11 — Vision, multimodal and design input

Design-to-code from a mockup, error-dialog triage from a photo, and image
diffing for visual regression.

## W12 — Memory, skills and playbooks

- Durable team memory beyond `project_rules`: learnings from finished runs,
  searchable and reviewable.
- Reusable playbooks / custom agents (the leaders' slash commands, subagents,
  microagents) with a permission model — a playbook must not grant capability.
- Hooks: run a customer script on tool-use / on-stop, inside the gate.

## W13 — BYO-runner: "full computer access" without dropping guardrails

Devin/OpenHands give a whole VM. Our answer is a runner the customer installs
on their own machine or CI box, executing with the same policy gate while the
harness keeps plan approval, checkpoints, metering and audit. This is the
capability users mean when they ask for full access — and the version that
doesn't turn us into a prompt-safety product.

**Gate:** a run executes on a customer-controlled host, the confinement
attestation is verifiable, and a stolen runner token cannot reach other teams.

## W14 — Model intelligence layer

Per-step model routing (cheap model for mechanical steps, frontier for
reasoning), eval harness for "which model is actually better on our repos",
cost/latency dashboards, and a rate card so unpriced models stop billing zero.

# PHASE 4 — Operate it as a company (W15–W18)

## W15 — Multi-tenant hardening

Per-team resource ceilings (partly done), noisy-neighbor tests, rate limits per
surface, secrets rotation runbook, backup/restore drill against real object
storage (the PITR drill exists — make it scheduled).

## W16 — Enterprise readiness

SCIM + group-mapped SSO, audit export to SIEM, customer-managed encryption
keys, residency options, pen test, counsel sign-off on the placeholder terms
(blocked on a human, tracked in `docs/backlog.md`).

## W17 — Reliability and scale

Load test at N hundred concurrent runs, event-bus backpressure, graceful
degradation when a provider is down, SLOs + error budgets, on-call runbooks,
status page.

## W18 — Launch

Docs site with a real quickstart, migration guide from Claude Code / Codex
(config + rules import), pricing page mapped to enforced caps (not aspirational
ones), public SDK, sample repos, and a demo that runs live rather than replaying
a recording.

# PART B — THE HERMES TRACK

`/Users/user/Compiler_Project`: ~14.2k lines of C++17, a dynamic language
(`.hms`), lexer → recursive-descent parser with multi-error recovery →
tree-walking interpreter **and** a stack-based bytecode VM, mark-sweep GC that
collects cycles, a `hermesc` CLI with 15 subcommands (repl/run/--vm/check/
compile/disasm/fmt/lint/lsp/json/install), a REPL with a persistent GC arena, a
530-case test suite, and CI on macOS + Ubuntu. Built as a university course
project; its own docs call it "a mature portfolio project, not production
software".

**What it is not, and we should not pretend otherwise:** no native codegen
(bytecode only), no real language server (the `lsp` subcommand is ~130 lines of
diagnostics-only JSON-RPC), no VS Code extension (`editors/vscode/` is a TextMate
grammar plus config), the GUI debugger replays a recorded trace rather than
suspending, and the parser is neither incremental nor lossless so it cannot back
an editor or symbol queries as it stands.

The value is not the code we can lift. It is three things nobody else can hand
us: a codebase we own completely, a **differential oracle** (both backends must
produce byte-identical output including error text, and the fuzzer's own
detection power was validated by injecting deliberate bugs), and the credibility
of shipping a language.

## H0 — Clear the rights before it becomes load-bearing (½ day, blocks everything)

Git history is single-author (41 commits, all yours) and there is **no LICENSE
file**, but the README presents it as a three-person course project with two
teammates' rows still `_add ID_`. Before Hermes is "an integral part of a
commercial product", two things need resolving, both cheap and both outside our
control once we start shipping:

- [ ] The university's student-IP policy for coursework. Some institutions claim
      a share of graded projects; some claim nothing. Get it in writing.
- [ ] A short written acknowledgment from the two named teammates, whatever they
      did or did not contribute, so no future claim rests on a README line.
- [ ] Then add a LICENSE. Recommendation: MIT for the language, grammar, LSP and
      editor plugins (they are the community wedge and worthless to us alone),
      and keep the compiler + toolchain under the product's own terms until we
      decide otherwise.

This is the same counsel queue that already holds `TERMS.md`/`PRIVACY.md`
(`docs/backlog.md`). Do it in W1 while it's still paperwork.

## H1 — Take the two designs, not the code (W1–W2, ~1 day)

- **The `--json` diagnostic contract.** Machine-readable
  `{path,line,col,kind,message}` on stderr, program output on stdout, never
  mixed. Adopt it verbatim as the harness's tool-output protocol — it is exactly
  what the W1 live transcript and the sandbox need, and it makes agent tool
  results parseable instead of scraped.
- **Differential verification as the review gate pattern.** Run baseline and
  agent-patched code over the same corpus and require byte-identical output
  where behaviour must not change; periodically plant a known bug and confirm
  the suite would have caught it. That last step — validating the validator — is
  the idea worth stealing, and it is what our "the tests the agent wrote pass"
  gate is missing.

## H2 — Hermes as a first-class language in the harness (W4–W5, ~1 week)

Ship the toolchain in the sandbox image and expose it as agent tools, so the
agent can work in a language whose semantics we can explain in an interview.

- `hermesc` in the confined runner; `run`, `check`, `disasm`, `fmt`, `lint`
  callable as structured tools with the H1 protocol.
- Toolchain detection in the planner, so a Hermes repo gets a Hermes plan.
- A **tree-sitter grammar** rather than pretending the existing parser can back
  editor features — it is non-incremental and lossy by design, and writing a
  grammar is days, not weeks, and immediately gives us highlighting, symbol
  extraction and the navigation queries the agent needs.
- Syntax highlighting in the web diff view from the existing TextMate grammar
  (the one genuinely reusable artifact in `editors/`).
- Formatter and linter as agent-callable cleanup steps, so style is enforced by
  a deterministic tool instead of model opinion.

**Gate:** an agent takes a seeded bug in a `.hms` file, fixes it, runs both
backends, and the differential check is part of the review evidence.

## H3 — Fix the language server, and let it carry the IDE (W7, +3–4 days)

The `lsp` stub is the weakest component and the highest-leverage one to fix,
because W7 needs LSP plumbing regardless. Doing it for a language we fully own
is the cheapest way to build and validate that machinery: hover, definition,
references, document symbols, rename, and incremental sync — the last one
handled by tree-sitter, not by the compiler's parser.

Ship `hermes-language-server` as open source. It is the reference implementation
every later language plugs into, it is a standalone reason for developers to
find us, and it turns "we also have a VS Code extension" from a claim into
something they can install today.

**Gate:** the W7 extension talks to `hermes-language-server` for a real repo,
and a second language can be added by writing an adapter, not by forking the
extension.

## H4 — The VM as a safe runtime for agent glue (W9–W10, ~1 week)

This is the genuinely differentiated one, and the strongest argument for keeping
Hermes at all.

The VM executes `.hms` with no filesystem, no syscalls and no network by
construction — the interpreter simply has no such capability wired in — and it
already supports a statement budget (`set_statement_limit()`) and GC pressure
controls. That is a **policy-free sandbox**: a place to run customer-authored
logic that cannot escape, without paying container startup latency or widening
the OS-confined runner.

What that buys us, none of which we can safely offer today:

- **Playbooks and hooks in Hermes** (W12). A team writes its own approval rules,
  post-edit checks, transforms and report generators in a real language, and we
  can say without qualification that the code cannot touch their machine.
  Everyone else's "custom hooks" run with the user's permissions.
- Agent-generated one-off scripts — data munging, migrations dry-runs, report
  formatting — executed and returned in milliseconds instead of provisioning a
  sandbox.
- A deterministic replay surface for the audit trail: the transcript can include
  the exact `.hms` that ran, and anyone can re-run it years later.

Guardrail worth stating plainly: the statement budget is **not** a security
boundary for anything that can reach a syscall. It is safe precisely because
this VM has no such bindings — keep it that way, and make "no host functions are
registered" an enforced test, not a convention.

**Gate:** a team-authored hook in Hermes runs inside a web request path with a
budget, cannot escape, is recorded in the audit trail, and a planted
`open("/etc/passwd")`-equivalent fails to compile because the binding does not
exist.

## H5 — Hermes as the product's scripting surface (W12, ~1 week)

Playbooks, custom agents and slash-command bodies authored in `.hms`, with the
gradual type checker (334 lines today, extend as needed) catching the common
mistakes before execution. This is where "we made a language" stops being a
party trick and becomes the extensibility story the leaders don't have: their
plugins are JavaScript with the user's full permissions.

## H6 — `hermes-bench`: the public eval corpus (W14, 2–3 days then ongoing)

Seeded bug classes in a real compiler codebase + the differential oracle = a
benchmark where a correct fix is *provable*, not judged by a model. Most agent
products benchmark on toy tasks because building a verifiable corpus is hard and
owning one is rare. We own one.

Use it internally to pick models per step (W14's routing), and publish it. A
leaderboard others can run against is the cheapest durable marketing asset in
this entire plan, and it is the one thing a competitor cannot copy without
writing their own language.

## H7 — Open the language, keep the platform (W16–W18)

Release the spec, the grammar, `hermes-language-server`, the VS Code extension
and `hermes-bench`. Keep the compiler's product integration, the sandbox
toolchain images and the eval harness on our side. A startup that ships a
language, a compiler, an LSP, a benchmark and an agent platform is telling a
different story than one that ships a ChatGPT wrapper, and the story is true.

## Hermes non-goals

Native machine-code generation (a research project, not a feature). The ImGui
GUI (irrelevant to the product). A stdlib beyond what hooks need. Rewriting any
part of the harness in Hermes — the platform stays Python and TypeScript. And
never requiring a customer to learn Hermes to use the product: H4/H5 are
opt-in surfaces, not a tax.

## Where Hermes touches the launch gate

H0, H1 and H2 are **in** the launch path — rights cleared, the diagnostic
protocol, and the differential review gate are all prerequisites for claiming
verified agent work. H3 ships with the W7 extension. H4–H7 are post-launch
differentiators and must not delay W18.

# Launch gate — all must be true

- [ ] A live run works on a healthy stack, and CI fails if any container is unhealthy
- [ ] Agent has read/write/edit/glob/grep/bash/web/MCP, each with a boundary test
- [ ] Live transcript, cost footer, interrupt, steer, rewind — all real, none decorative
- [ ] Screenshot in, screenshot out; browser-verifiable frontend work
- [ ] Parallel isolated runs in one repo
- [ ] CLI + IDE extension, both passing through the same policy gate
- [ ] Prompt → preview → deploy → share link
- [ ] Team memory, playbooks, hooks, with no capability escalation path
- [ ] BYO-runner with verifiable confinement attestation
- [ ] Rate card covering every listed model, or "cost not tracked" stated in-product
- [ ] Hermes rights cleared in writing and a LICENSE chosen (H0) — before it is load-bearing
- [ ] `--json` diagnostic protocol is the contract for every tool result (H1)
- [ ] Review evidence includes a differential run, not just the agent's own tests (H1/H2)
- [ ] Hermes toolchain ships in the sandbox image with a tree-sitter grammar (H2)
- [ ] Zero fake affordances in the UI (standing audit), zero AA contrast failures
- [ ] Pen test complete, counsel-approved terms, SSO/SCIM, audit export
- [ ] SLOs defined, backup/restore drilled, on-call documented

# What could break this plan

1. **SDK internals are a black box.** Cancellation, in-loop approval and the fs
   tool's scope behaviour are all guesses until spiked. Each could turn a 3-day
   task into a 3-week one. W1–W3 each start with a timeboxed spike for exactly
   this reason.
2. **The contract freeze.** Two bumps are scheduled; a third means re-planning
   the week it lands in.
3. **Security debt we've already found.** `python -c` bypasses the path scope
   check; Landlock v1 has no network hook so Linux confinement is really the
   container; the egress proxy was down for hours unnoticed. Widening the
   agent's reach before these are closed is how a governance product loses the
   right to call itself one.
4. **Two things only you can do:** the in-loop approval policy call (W3) and
   counsel sign-off (W16).
5. **Hermes is the easiest thing in this plan to over-invest in.** It is *our*
   code, so every estimate feels controllable and every refactor is inviting —
   and it is a compiler, so the work never ends. H0–H2 are load-bearing for the
   launch claim of verified agent work; H3–H7 are explicitly post-launch and
   must not move W18. If a Hermes task slips twice, it moves to the backlog
   rather than pushing the launch.
6. **Scope honesty.** This plan does not include a model of our own, mobile
   apps, voice, or an IDE of our own. If any of those is actually the product,
   say so now — it changes the shape of the roadmap, not just its length.

# Recommended sequencing decision

Two honest options, and the difference is launch date, not ambition.

**A — Launch the platform first (recommended).** W1–W6 + H0–H2, then W18. A
governed agent with a CLI, a live transcript, a differential review gate and a
Hermes toolchain that proves it works on a hard codebase. Roughly 8 weeks.
H3–H7 and W7–W17 continue after, funded by design partners.

**B — Launch the whole story.** All 20 weeks, including the IDE extension with
`hermes-language-server`, the safe hook runtime and `hermes-bench` public at
launch. Roughly 20 weeks solo, 12 with two engineers, and materially more risk
of shipping nothing while everything is 80% done.

The reason to prefer A is that H6 is the strongest card in this plan and it does
not need a launch to be played: a provable benchmark and a public leaderboard can
be built during W1–W6 in the background and released whenever it is ready. That
gets the credibility of "they wrote a language and a compiler and an eval suite"
without paying for the IDE surface first.
