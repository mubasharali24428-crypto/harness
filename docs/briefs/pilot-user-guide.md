# Shared-run pilot: engineer guide

This is a supervised two-week pilot for 1–2 allowlisted teams, not a production-readiness claim. A human supervisor watches the audit log. [U1]

A shared run lets teammates follow one agent run, send direction, transfer its session leadership and review withheld high-impact changes. Team roles and session leadership are different: engineers/admins can write; viewers/guests join as observers and cannot steer. One joined engineer/admin can lead a run. The leader decides high-impact requests, changes scope/permission guidance and offers handoff; ordinary joined engineers can send guidance. [U2]

1. Sign in and open the run link supplied by your team (`/projects/<projectId>/runs/<runId>`). Choose **Join this run**. If there is no leader, an engineer/admin can choose **Become session leader**. There is no forced takeover of an existing leader. [U3]
2. Under **Give direction**, choose Guidance, write a clear instruction and choose **Send direction**. The next engine call receives it; an in-progress call does not. Only the leader can choose scope/permission changes, and a reason is required. These invalidate pending/approved approvals. A permission-change message does not change the sandbox policy. [U4]
3. To transfer leadership, the current leader chooses a joined engineer/admin and **Offer handoff**. The recipient chooses **Accept** or **Decline**. The original leader stays in charge until acceptance. If the leader is unavailable, contact the supervisor: the product has no forced takeover button. [U5]
4. In **Decisions**, read the action, files, summary and proposed change. The leader chooses **Approve this change** or **Reject**. For staged changes, the digest binds full old/new file bytes even when the display is clipped; apply checks and lands the same withheld snapshot. Approval is tied to the proposal digest and expires by default after one hour. A requester cannot approve their own request under pilot settings: transfer leadership to another eligible person if needed. For a staged change, approval is only the first step; the leader must choose **Apply approved change**. Pending approvals block the next execution; open staged approvals block completion/PR creation. [U6]
5. To stop, an engineer/admin uses **Stop** in run controls. A `stopping` response is not confirmation that the worker has stopped. Ask the supervisor to confirm `run.cancel_confirmed`; report an unconfirmed stop immediately. [U7]

**“Shared runs are not enabled for your team yet”** means your team is outside the collaboration allowlist. Polling stops. Ask the supervisor to verify enrollment; do not switch teams or widen permissions to bypass the notice. [U8]

Known limits: updates are polled every three seconds, with no online/presence indicator. Guidance delivery is recorded after the engine returns; a crash before that record can cause redelivery (delivered items are numbered, and the agent is told to skip numbers it already acted on). Staging works at file level after engine calls, not as approval on every internal tool call. The displayed diff is shortened after 4,000 characters; do not treat a clipped view as a complete review. Generic completion can report a staged request done without landing its files: use Apply. [U9]

Current workspace provisioning creates a new workspace on first start, empty or copied from an operator-prepared directory selected by `HARNESS_WORKSPACE_SEED` (with `.git` skipped); it does not fetch a GitHub repository. Existing runs keep their copies. The release evidence does not cover real inbox delivery or multi-user collaboration on the real model. No measured baseline or completed real pilot is claimed. [U10]

Recommended problem report to your designated supervisor: run/project ID, time and timezone, expected versus actual behavior, action taken, visible error code/request ID, and whether Stop was confirmed. Include a redacted screenshot only if useful. Never include OTPs, keys or credentials. No dedicated problem-reporting feature is claimed. [U11]
