## 1. Backup and WAL alerts are no longer inert (part 28)

- `deploy/runners/backup.sh` inserts a `backup_runs` row (migration 0059) only after its storage
  post-check proves the base backup landed. A failed insert is logged and the stale alert then fires.
- The orchestrator's domain poll (`deploy/runners/observability.py::_read_backup_gauges`, every
  `HARNESS_METRICS_DB_POLL_SECONDS`) exposes `harness_backup_last_success_timestamp_seconds` (newest
  `backup_runs` row) and `harness_pg_wal_archive_failed_count_total` (`pg_stat_archiver.failed_count`).
  Unknown values (SQLite, no backup yet) render no sample rather than a false zero.
- `alerts.yml` descriptions and `docs/runbooks/alerting.md` (d), (e) and section 5 now describe the
  emitters. `promtool check rules`: SUCCESS, 16 rules.
- Test: `section1/tests/test_backup_metrics_pg.py` (PG 18, every migration): the WAL counter equals
  `pg_stat_archiver.failed_count`; the backup series is absent with no row and equals the newest row
  after an insert. `test_deploy_observability.py` 23 passed. `migrate_selftest`: 59 migrations
  (0001 to 0060) apply clean and re-run idempotently.

Limit: a stack that never ran a backup has no series, so `HarnessBackupStale` cannot fire there; a
deployment that relies on backups should add `absent(harness_backup_last_success_timestamp_seconds)`.

## 4. Live WAL-G drill on the compose primary (part 28), 2026-10-21

**A real failure first.** The stack had been brought up at 04:06 UTC with
`docker compose --env-file .env -f deploy/docker-compose.yml up -d` (the form in
`docs/runbooks/alerting.md`). `--env-file` replaces compose's project `.env`, so `deploy/.env`, the only
file setting `WALG_FILE_PREFIX`, was skipped: the live `db` ran with no archive target and every
`wal-g wal-push` failed ("Failed to find any configured storage"). The emitter and the rule caught it:
`harness_pg_wal_archive_failed_count_total` matched `pg_stat_archiver.failed_count` (24), and
`HarnessWalArchiveFailing` (severity page) was emailed through Alertmanager to the Mailpit catcher at
04:07:25 UTC, about a minute after the bad `up`. Nobody read that mailbox for 3 h. That is the single-channel
limit, now seen live. An orphaned wal-g `BASE_BACKUP` walsender from the paused drill was still waiting for the archive.

Fix (local, gitignored): the root `.env` now sets `WALG_FILE_PREFIX=/tmp/harness-walg-live`, the same value
as `deploy/.env`. The orphan was terminated and only `db` was recreated (`up -d --no-deps db`). Segments
`...84` to `...8D` were archived with `failed_count` 0.

**Drill** (`docker compose --env-file .env -f deploy/docker-compose.yml --profile walg run --rm --no-deps walg`;
`--no-deps` keeps `walg-db`, another timeline-1 cluster, from archiving into the live repository):

| check | result |
|---|---|
| streaming base backup of `db` | `base_00000001000000030000008F`, 07:32:21 to 07:32:23 UTC (2 s), exit 0 |
| archiver post-check | `last_archived_wal=...8F.00000028.backup`, age 1 s |
| storage inventory (`BACKUP_MODE=list`) | one full backup, start/finish LSN `3/8F000028`/`3/8F000120` |
| `backup_runs` row | id 1, kind `base`, `finished_at` 07:32:24.012 UTC (epoch 1792567944.01) |
| orchestrator `/metrics` | `harness_backup_last_success_timestamp_seconds 1792567944.012408`, `harness_pg_wal_archive_failed_count_total 0` |
| Prometheus | `time() - harness_backup_last_success_timestamp_seconds` = 25 s (`HarnessBackupStale` threshold 90000 s) |

After the drill the compose journey passed 12/12 on the recreated `db`.

Limits: file storage on the same host, not object storage. No restore was taken from this backup (the Session 12
rollback rehearsal restores a `pg_dump`, not WAL-G, `evidence/s12/part59.md`; row 53 keeps the real-restore cap). One
email address is still the only alert channel.

(`harness-pitr`, volume `harness_pgdata_pitr`) with `WALG_FILE_PREFIX=/tmp/harness-walg-live deploy/walg/restore-walg.sh`.

`id=99` inserted after it, `pg_switch_wal()`, segment `...9F` archived, `failed_count` 0.

primary server, where its value was 120". The live `db` gets `max_connections=120` as a compose `-c` flag, which
is not in the fetched `postgresql.conf`. The August drills restored `walg-db`, which runs the defaults, so they
never hit this. Fix: `restore-walg.sh` now starts the scratch server with `-c max_connections=120`.
